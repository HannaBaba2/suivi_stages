## 3. Le modèle Entreprise

### Je réfléchis aux champs

- nom : texte, et je le rends **unique** pour éviter les doublons
- ville : texte
- secteur : une **liste de choix**, pas du texte libre, sinon tout le monde
  va écrire "informatique" différemment
- email : pas un texte normal, un champ spécial qui vérifie le format
- "on veut la reconnaître sans cliquer" : ce n'est pas un champ, c'est la
  méthode `__str__` qui doit renvoyer le nom

### J'écris le modèle

Dans `stages/models.py` :

```python
from django.db import models


class Entreprise(models.Model):

    SECTEUR_CHOICES = [
        ("informatique", "Informatique"),
        ("banque", "Banque"),
        ("sante", "Santé"),
        ("autre", "Autre"),
    ]

    nom = models.CharField(max_length=150, unique=True)
    ville = models.CharField(max_length=100)
    secteur = models.CharField(max_length=20, choices=SECTEUR_CHOICES)
    email = models.EmailField()

    def __str__(self):
        return self.nom
```

### Je commit

```bash
git add stages/models.py
git commit -m "Ajoute le modèle Entreprise

Nom unique pour éviter les doublons, secteur en liste fermée pour
éviter les variantes de saisie, EmailField pour valider le format."
```

### 3.2 Je migre

```bash
uv run manage.py makemigrations stages
uv run manage.py sqlmigrate stages 0001
uv run manage.py migrate
```

**a. Où est la contrainte anti-doublon dans le SQL ?**
Je la vois sur la colonne `nom`, avec le mot-clé `UNIQUE`. C'est elle qui
empêche d'enregistrer deux fois le même nom.

**b. Une colonne que je n'ai pas écrite ?**
La colonne `id`. Django l'ajoute tout seul comme clé primaire, même si je
n'ai rien demandé.

**c. Je change `max_length` et je relance `makemigrations`**
Django crée un **deuxième** fichier de migration (`0002_...`), il ne modifie
pas le premier. Pour revenir en arrière, je peux :

```bash
uv run manage.py migrate stages 0001
```
puis supprimer le fichier `0002_...py`.

### Je commit les migrations

```bash
git add stages/migrations/
git commit -m "Ajoute la migration initiale du modèle Entreprise"
```

Si j'ai changé `max_length` :

```bash
git add stages/models.py stages/migrations/
git commit -m "Ajuste la longueur du champ nom"
```

## 5. La première page

### La vue

Dans `stages/views.py` :

```python
from django.shortcuts import render
from .models import Entreprise


def liste_entreprises(request):
    entreprises = Entreprise.objects.all()
    return render(request, "stages/liste_entreprises.html", {"entreprises": entreprises})
```

### Le template

Django cherche les templates dans `stages/templates/stages/`. Je crée donc
`stages/templates/stages/liste_entreprises.html` :

```html
<h1>Entreprises</h1>

{% if entreprises %}
<ul>
  {% for e in entreprises %}
  <li>{{ e.nom }} — {{ e.ville }} — {{ e.secteur }}</li>
  {% endfor %}
</ul>
{% else %}
<p>Aucune entreprise enregistrée.</p>
{% endif %}
```

### Les urls

`stages/urls.py` (nouveau fichier) :

```python
from django.urls import path
from . import views

app_name = "stages"

urlpatterns = [
    path("entreprises/", views.liste_entreprises, name="liste_entreprises"),
]
```

`suivi_stages/urls.py` (je complète) :

```python

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("stages.urls")),
```

### Je teste l'erreur volontaire

Je déplace le template, je recharge la page.

**a. Que liste la page d'erreur ?**
Elle liste tous les dossiers où Django est allé chercher le template et n'a
rien trouvé. Ça me dit exactement où il l'attendait  donc où le remettre.

**b. Cette page bavarde s'affichera-t-elle en production ?**

Non, seulement si `DEBUG = True` dans `settings.py`. En production, ce
réglage doit être `False`, et Django affiche une page d'erreur générique à
la place.

## Restitution : je prépare mes réponses (pas de code)

**1. Retrouver le même environnement dans trois mois, sur une autre machine :**
```bash
git clone <mon-dépôt>
cd suivi_stages
uv sync
```
Ce qui garantit que c'est *exactement* le même environnement, c'est
`uv.lock` : il fixe les versions précises de Python et de chaque dépendance,
pas juste des plages de versions.

**2. Qui décide de la forme de la table : models.py, la migration, ou la base ?**
`models.py` exprime mon intention. Le fichier de migration est la **traduction
en instructions** de cette intention. La base ne fait qu'exécuter ces
instructions. Donc `models.py` décide, la migration transmet, la base
applique.

**3. Les deux erreurs provoquées, qu'est-ce qui m'a mis sur la voie ?**
- L'erreur de `makemigrations` avant d'avoir déclaré l'app dans
  `INSTALLED_APPS` : le message nomme précisément l'app introuvable.
- L'erreur `TemplateDoesNotExist` : le message liste tous les chemins
  essayés, ce qui montre où le fichier était attendu.
